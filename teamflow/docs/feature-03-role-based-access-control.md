# Feature 3: Role-Based Access Control & Invite Flow

---

## 1. What problem does this feature actually solve?

Once multiple people are inside the same team workspace, not everyone should
be able to do everything. A regular team member should be able to create and
update tasks — but they shouldn't be able to fire a colleague, cancel the
company's subscription, or invite strangers into the workspace. Only specific
people with the right level of authority should have access to those actions.

Without this feature, every person inside an org would have the same unlimited
power. One misclick by a junior employee could delete the entire company's
projects. One disgruntled member could invite outside people in.

This feature solves two problems together:

- **Role enforcement:** Every sensitive action (inviting people, changing
  roles, removing members, managing billing) is locked behind a role check.
  If you don't have the right role, you get blocked before the action even
  starts — not after.

- **Invite flow:** New teammates can't just sign up and claim to be part of
  your company. They need a special invite link, generated by someone who
  already has permission to add people, that expires after 48 hours and can
  only be used once.

---

## 2. Step-by-step story of what happens when it runs

### Part A: How roles are checked on every request

Picture Rajan, a regular Member at Acme Corp, trying to invite his friend to
the workspace by visiting the "Send Invite" button. Here's what happens:

1. His request arrives at the server with his login token.

2. The server reads his token, extracts his user ID and org ID, then checks
   the database to confirm he's actually a member of Acme Corp — and reads
   his current role directly from the database. His role turns out to be
   "member."

3. The invite endpoint has a guard on it: `requireRole('admin')`. This guard
   checks: "Is Rajan's role at least 'admin'?" The answer is no — he's just
   a "member," which ranks below "admin."

4. The request is immediately rejected with a "403 Forbidden" error message:
   "This action requires the 'admin' role or higher." Rajan's request never
   reaches the actual invite logic. Nothing is created. Nothing is changed.

The key insight: the role check happens in the *middleware* — the layer
between "request received" and "actual code runs." The actual invite function
never even gets called.

### Part B: How the invite flow works

Now picture Priya, the Owner of Acme Corp, inviting her colleague Dev to join.

**Sending the invite:**

1. Priya types Dev's email address and clicks "Send Invite."

2. The server checks Priya has the admin or owner role. She does — she's Owner.

3. The server checks there isn't already a pending invite for Dev's email at
   Acme Corp, and that Dev isn't already a member. Clean — proceed.

4. A special one-time invite token is created. It's a cryptographically
   signed string (a JWT) that encodes: Dev's email, Acme Corp's ID, the role
   they'll receive (e.g., "member"), and an expiry timestamp 48 hours away.

5. This token is also saved to the database so it can be tracked, revoked,
   and marked as used.

6. The server prints the invite link to the console (in production this
   would be emailed). The link looks like:
   `http://localhost:5173/accept-invite?token=eyJ...`

7. Priya copies the link and sends it to Dev over Slack.

**Accepting the invite:**

1. Dev clicks the link. The browser shows an "Accept your invite" page with a
   password field.

2. Dev types a password and clicks "Join workspace."

3. The server verifies the token's cryptographic signature (it hasn't been
   tampered with) and checks the expiry (not expired).

4. It also checks the database record: has this invite already been accepted?
   Has it been revoked? If either is true — blocked.

5. If everything is clean: Dev's user account is created (or if Dev already
   has an account with that email, they're just added to the new org).

6. A row is added to `org_members` connecting Dev to Acme Corp with the role
   "member."

7. The invite is marked as "accepted" with a timestamp — it can never be
   used again.

8. Dev gets a fresh login token and lands inside Acme Corp's workspace.

## 3. A real-world analogy

Think of a building with different keycards.

The **role system** is like keycard access levels. A regular employee's card
opens their office floor and the kitchen — but not the server room, the
executive suite, or the HR filing cabinet. A manager's card opens more doors.
The CEO's card opens everything. When someone tries to open a door their card
doesn't cover, the card reader beeps and the door stays locked — the door
doesn't ask questions or explain itself, it just enforces the level.

The **invite flow** is like a visitor badge that a receptionist prints for
a specific guest. It has the guest's name on it, a date it expires, and it
only unlocks certain doors (their role). The guest can't print their own
badge — only the receptionist can. And once the guest uses it to check in,
the badge is marked as used and can't be used again to let someone else in.

## 4. The ONE thing that would impress an interviewer

**The invite token is stored in the database even though it's already a signed JWT.**

A common shortcut would be to only use the JWT: verify the signature, trust
the payload, done. But that has a flaw — **JWTs cannot be revoked.** If
Priya sends an invite to someone, changes her mind, and tries to cancel it,
the JWT is already out there. If the recipient has the link, they can still
use it until it expires 48 hours later.

By also storing the token in a database table, you get two things JWTs
alone can't give you:

1. **Revocability** — deleting the database row makes the invite invalid
   immediately, even if the JWT signature is still valid. The acceptance
   code checks the database record, not just the signature.

2. **Auditability** — you can see who invited whom, when, and whether it
   was accepted or still pending. The Team page uses this to show a list of
   pending invites that owners and admins can track and cancel.

The phrase for an interview: "I used a JWT for the invite token because it's
self-contained and portable, but I also stored it in the database to support
revocation — since JWTs alone can't be invalidated once issued."

## 5. Likely interviewer follow-up, and how to answer it

**Question:** "Your `requireRole` middleware re-reads the user's role from
the database on every request instead of trusting the JWT. Doesn't that add
an extra database query to every single request?"

**Answer:** Yes, it does — one extra query per authenticated request in
`verifyOrgMembership`. But it's the right tradeoff for two reasons.

First, **correctness over micro-optimization.** If you trust the role from
the JWT, a user who gets demoted from Admin to Member keeps admin-level
access until their token expires — potentially hours or days. That's a real
privilege escalation window.

Second, **the query is cheap and already necessary.** We have to hit
`org_members` anyway to verify the user actually belongs to the org in their
JWT (since `org_members` isn't RLS-protected). Reading the role in the same
query costs nothing extra — it's a single indexed lookup on a small table
that returns one row.

In a very high-traffic system, you could cache the role in Redis with a
short TTL (say, 60 seconds) to reduce DB load while keeping the staleness
window acceptably small. But for most applications, the single indexed
query is negligible.

## Email Integration — Resend

Invite links are now delivered by email using [Resend](https://resend.com),
a transactional email API with a generous free tier (100 emails/day, no
credit card required).

### What the email contains

- Subject: `[Inviter's email] invited you to join [Org name] on TeamFlow`
- A short message explaining the invite and the role being granted
- A prominent "Accept Invite" button linking to `/accept-invite?token=...`
- A note that the link expires in 48 hours
- A plain-text URL fallback for email clients that don't render HTML

### From address

`TeamFlow <onboarding@resend.dev>` — Resend's shared test domain, which
works out of the box without domain verification. For production, verify
your own domain in the Resend dashboard and update `FROM_ADDRESS` in
`src/lib/email.js`.

### Graceful failure design

Email delivery failure **never blocks invite creation**. The flow is:

```
1. DB: insert invite_tokens row              ← if this fails, throw (invite blocked)
2. DB: fetch inviter email + org name        ← for the email body
3. Email: sendInviteEmail()                  ← if this fails, log + continue
4. Return { inviteUrl, token }               ← invite always succeeds if DB did
```

`sendInviteEmail()` is written to never throw — it catches both Resend
API errors (bad key, rate limit, domain not verified) and network errors,
logs them with `[email]` prefix, and returns `false`. The invite record
is already committed to the database at the point the email fires, so
the invitee can always be resent a link manually from the Team page.

This matters because email delivery is an external dependency with its
own failure modes entirely separate from your application's correctness.
Coupling invite creation to email delivery would mean a Resend outage
prevents your team from growing — which is the wrong tradeoff.

### Environment variable

Add to `backend/.env`:

```
RESEND_API_KEY=re_xxxxxxxxxxxxxxxxxxxx
```

Get this from [resend.com/api-keys](https://resend.com/api-keys).

If the key is missing or still set to the placeholder `re_REPLACE_ME`,
email is skipped silently and the invite link is only logged to the
console — the same behaviour as before this integration was added.
